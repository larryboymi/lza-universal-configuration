

== Log Analysis

=== Overview

The LZA Universal Configuration centralizes organizational logs into a single S3 bucket (`aws-accelerator-central-logs-{ACCOUNT_ID}-{REGION}`) in the LogArchive account. This bucket receives CloudTrail, AWS Config, VPC Flow Logs, GuardDuty findings, and Session Manager logs from all accounts in the organization.

Once access is granted, you can analyze these logs using Amazon Athena for SQL-based queries, Amazon OpenSearch Service for full-text search and dashboards, Amazon CloudWatch Logs Insights for real-time analysis, or third-party SIEM platforms such as Splunk.

This section covers how to grant access to the centralized log bucket for these tools.

=== Default Security Posture

The centralized logging bucket is deployed with a security-by-default approach. The bucket policy restricts access to:

* LZA-managed roles (`AWSAccelerator-*`, `cdk-accel-*`)
* The management account access role
* AWS service principals (CloudTrail, Config, VPC Flow Logs, SSM) for log delivery

By default, no external principals (such as log analysis tools or SIEM platforms) have access to read objects in this bucket. This ensures log data remains protected until explicit access is granted.

=== Adding Access for Log Analysis Tools

Organizations commonly need to grant access to tools such as Splunk, Amazon OpenSearch Service, or other SIEM platforms to analyze centralized logs. LZA provides two approaches to extend the bucket policy without modifying LZA-managed resources directly.

==== Option 1: Append Additional Policy Statements (Recommended)

Use `s3ResourcePolicyAttachments` to add policy statements to the existing LZA-managed bucket policy. This approach preserves the default security controls while granting additional access.

**Step 1:** Create a `s3-policies/` directory in your LZA configuration repository (at the same level as your YAML config files).

**Step 2:** Create the S3 policy file at `s3-policies/central-log-bucket-read-access.json`:

[source,json]
----
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowLogAnalysisToolAccess",
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::111111111111:role/SplunkIngestionRole",
          "arn:aws:iam::111111111111:role/OpenSearchAccessRole"
        ]
      },
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::aws-accelerator-central-logs-222222222222-us-east-1",
        "arn:aws:s3:::aws-accelerator-central-logs-222222222222-us-east-1/*"
      ]
    }
  ]
}
----

Replace the following values with your environment-specific details:

* `111111111111` — The AWS account ID where your log analysis tool runs
* `SplunkIngestionRole` / `OpenSearchAccessRole` — The IAM role name your tool uses to access S3
* `222222222222` — Your LogArchive account ID
* `us-east-1` — Your home region

**Step 3:** Create a `kms-policies/` directory and add `kms-policies/central-log-bucket-key-access.json` (required to decrypt log objects):

[source,json]
----
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowLogAnalysisToolDecrypt",
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::111111111111:role/SplunkIngestionRole",
          "arn:aws:iam::111111111111:role/OpenSearchAccessRole"
        ]
      },
      "Action": [
        "kms:Decrypt",
        "kms:DescribeKey"
      ],
      "Resource": "arn:aws:kms:us-east-1:222222222222:key/KEY_ID_HERE"
    }
  ]
}
----

Replace the `Resource` value with the ARN of the KMS key used to encrypt the central log bucket. You can find this key ARN in the SSM parameter `/accelerator/kms/s3/key-arn` in your LogArchive account.

**Step 4:** Add the policy references to `global-config.yaml` under the `centralLogBucket` section:

[source,yaml]
----
  centralLogBucket:
    s3ResourcePolicyAttachments:
      - policy: s3-policies/central-log-bucket-read-access.json
    kmsResourcePolicyAttachments:
      - policy: kms-policies/central-log-bucket-key-access.json
    lifecycleRules:
      - enabled: true
        abortIncompleteMultipartUpload: 7
        expiration: 1000
        noncurrentVersionExpiration: 1000
        transitions:
          - storageClass: GLACIER_IR
            transitionAfter: 365
        noncurrentVersionTransitions:
          - storageClass: GLACIER_IR
            transitionAfter: 365
----

**Step 5:** Deploy the changes by uploading the updated configuration and running the LZA pipeline.

[NOTE]
====
Policies added via `s3ResourcePolicyAttachments` persist across LZA pipeline runs. LZA will not overwrite your custom policy statements — it appends them to the managed policy on each deployment. You do not need to reapply these after upgrading LZA.
====

==== Option 2: Fully Replace the Bucket Policy

Use `customPolicyOverrides.s3Policy` to completely override the LZA-managed bucket policy with your own. Use this approach only when you need full control over the policy document.

[source,yaml]
----
  centralLogBucket:
    customPolicyOverrides:
      s3Policy: s3-policies/central-log-bucket-policy.json
      kmsPolicy: kms-policies/central-log-bucket-key-policy.json
----

[IMPORTANT]
====
When using `customPolicyOverrides`:

* Your policy file must contain the **complete** policy document, including all necessary permissions for AWS services (CloudTrail, Config, VPC Flow Logs) to continue delivering logs
* `s3ResourcePolicyAttachments` cannot be used simultaneously with `customPolicyOverrides.s3Policy`
* `kmsResourcePolicyAttachments` cannot be used simultaneously with `customPolicyOverrides.kmsPolicy`
* You are responsible for maintaining the policy as LZA evolves — **LZA will not update your custom policy on subsequent deployments**
* If LZA adds new service principal requirements in future releases, you must manually add them to your policy
====

=== Key Constraints

* Policy file paths are relative to your LZA configuration directory (the directory containing your YAML config files)
* When Block Public Access is enabled (default), you cannot specify a policy that makes the bucket public
* The `importedBucket.applyAcceleratorManagedBucketPolicy` cannot be `true` when `customPolicyOverrides.s3Policy` is defined
* Policy files must be standard IAM policy documents in JSON format

=== Directory Structure

After adding policy files, your configuration directory should look like:

----
your-config/
├── global-config.yaml
├── accounts-config.yaml
├── ...
├── s3-policies/
│   └── central-log-bucket-read-access.json
└── kms-policies/
    └── central-log-bucket-key-access.json
----

=== Recommended Approach

For most use cases, Option 1 (`s3ResourcePolicyAttachments`) is recommended because:

* The LZA-managed policy continues to receive security updates as the solution evolves
* Existing security controls remain intact
* Additional access is explicitly added without risk of accidentally removing required permissions
* Easier to audit — your additions are in a separate file from the base policy
* No maintenance burden when upgrading LZA versions

Use Option 2 (`customPolicyOverrides`) only when you require complete control over the policy document and accept responsibility for maintaining all necessary service permissions across LZA upgrades.
